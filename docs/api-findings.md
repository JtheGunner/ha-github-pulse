# API and platform findings (Phase 0)

Results of the Phase 0 spikes (HGP-9 to HGP-14). Everything here was checked against the live GitHub API or the Home Assistant core source in October 2026 (HA `2026.10.x`). Sample data is limited to the maintainer's account; where that limits the conclusion, it is said so.

## P0-1 Permission matrix

Generated by `scripts/generate_permission_matrix.py`, output in [`permission-matrix.md`](permission-matrix.md).

- Fine-grained permission categories come from GitHub's published data, so no fine-grained token is needed to build the matrix. The classic-scope column is probed live.
- **Not verified:** whether GraphQL `contributionsCollection` works with a fine-grained PAT. This needs a fine-grained test token; until then the config flow must probe it at runtime instead of assuming.
- GraphQL requires authentication (`403` without a token). REST reads for public data work anonymously but with the low anonymous rate limit.
- Confirmed unsupported for fine-grained PATs: Packages and notifications.

## P0-2 Contribution calendar time zone

The contribution calendar and `contributionsCollection` bucket days in **America/Los_Angeles** (Pacific Time, with daylight saving), not UTC. Evidence: every `occurredAt` value in summer is `T07:00:00Z`, and in March it is `T08:00:00Z` (standard time).

Consequences:

- A "month" in the integration must use the same day boundaries as GitHub, otherwise totals differ from github.com.
- Window boundaries are computed as midnight in the contribution time zone, converted to UTC.
- The zone is configurable in the options flow. Default `America/Los_Angeles`. A user whose GitHub profile has another time zone set should enter it. The API does not expose the profile time zone (`timezone` was unset in the REST profile response).
- The calendar window limit of one year and the cost of 1 point per request were re-confirmed.

Not verified: whether a profile time zone, once set, changes the bucketing. Only the default behaviour was observed.

## P0-3 Packages download statistics

- GraphQL exposes `PackageVersion.statistics.downloadsTotalCount` and `Package.statistics.downloadsTotalCount`. Neither field is deprecated.
- Reading any package field requires the classic `read:packages` scope. The maintainer's token lacks it, so no live values were retrieved.

**Decision: conditional go.** Module P7-4 stays experimental. Before building it, retrieve live values with a token that has `read:packages`.

## P0-4 Home Assistant internals

Verified in the `home-assistant/core` source (`2026.10.x`):

| Assumption | Result |
| --- | --- |
| Enabling a disabled entity reloads the config entry | **Yes.** The config entries registry listener schedules a reload 30 seconds after the last entity registry change (`RELOAD_AFTER_UPDATE_DELAY = 30`). Demand-based fetching is therefore viable. |
| Config subentries | Present (`ConfigSubentry`, `ConfigSubentryFlow`, `async_get_supported_subentry_types`). |
| Statistics import | `async_import_statistics(hass, metadata, statistics)` and `async_add_external_statistics(...)`. `StatisticMetaData` requires `mean_type` (enum `NONE`/`ARITHMETIC`/`CIRCULAR`) and `unit_class`; `has_mean` is removed in 2026.4. |
| Service responses | `SupportsResponse` with `NONE`, `OPTIONAL`, `ONLY`. |
| Test environment | HA core requires Python `>=3.14.2`. Tests run with `pytest-homeassistant-custom-component`. |

Not tested in a running harness: the end-to-end behaviour of a subentry flow and a statistics import. These are covered by the tests of the tasks that build them.

## P0-5 Language estimate accuracy

Method: for two repositories, compare the repository language byte shares (the estimate's input) with the share of changed lines per language across the owner's last 40 commits (the ground truth), counting only programming languages.

| Repository | Ground truth (programming languages) | Estimate (repo byte share) |
| --- | --- | --- |
| Go project | Go 98 %, Go Template 1 %, Shell 1 % | Go 97 %, Go Template 2 %, Shell 1 % |
| Python project | Python 100 % | Python 100 % |

Findings:

- For single-language-dominated repositories, the estimate matches the ground truth within a few percentage points.
- A large share of changed lines is prose or configuration (51 % Markdown in one repository, 6-11 % in the other). The estimate does not count these. This is intended: the sensor reports *programming* languages.
- **Limit of this evidence:** both samples are dominated by one language. Repositories with a real mix (for example a PHP backend with a large Bash toolchain) were not measured, and that is where the estimate is expected to deviate most.

Recommendation: default weighting `commit-weighted`; keep `repo-count` as an alternative; label the result `estimated` everywhere.

## P0-6 Decisions taken

- **Minimum Home Assistant version: `2026.9.0`.** Two reasons: `has_mean` is gone from the statistics metadata (single code path with `mean_type` and `unit_class`), and HA replaced `voluptuous` with `probatio` as its validation library in 2026.9 and dropped `voluptuous` from its requirements, so integrations must import `probatio`. CI tests against the latest release only.
- Contribution time zone is an option (see P0-2).
